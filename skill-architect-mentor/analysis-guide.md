# 分析方法论：7 阶段拆解

> 本文件是 SKILL.md 在「深度分析」环节的详细展开。
> 核心原则：**重点不是罗列功能，而是回答「为什么这样设计」。**
> 每个阶段都标注了它对应报告的哪些章节——确保报告不漏项。
>
> 三条写作原则（贯穿全文）：
> - **原文佐证**：分析某个设计时，引用一段原文（skill 的描述、关键代码、模板片段）作为证据——既避免空谈，也让读者能对照原作加深理解。用引用块 `>` 或代码块呈现，每处引用控制在几行内。
> - **术语就近解释**：读者可能不熟悉 skill 里的技术细节。出现专业术语 / 技术概念时（如 wbi 签名、SSR、适配器模式、deletion test），紧跟一句简短解释（括号内或单列一行），再继续分析。宁可多解释一句，也别让读者卡在生词上。
> - **英文原文附翻译**：引用的原文若是英文，紧跟一句中文翻译（引用块后加「（中文：…）」）。

## 阶段 → 报告章节 映射

| 分析阶段 | 报告章节 |
|---|---|
| Phase 1 获取与建图 | §1 基本信息 |
| Phase 2 定位 | §2 解决的问题、§3 核心思想 |
| Phase 3 架构拆解 | §4 架构分析 |
| Phase 4 Workflow 分析 | §5 Workflow 分析 |
| Phase 5 Prompt 工程分析 | §6 Prompt 技巧分析 |
| 文件 / 代码结构 | §7 文件和代码设计分析 |
| Phase 6 设计经验提炼 | §8 最值得学习的 10 个设计点、§9 可以迁移的方法 |
| Phase 7 反向重设计 | §10 如果重新设计 |
| 用户自身反思 | §11 SOP |

> 此外，报告顶部有一个**不对应任何 phase** 的「输入与输出（速览）」节：从 skill 的 description + 流程，提炼出它需要什么输入、产出什么，配一个 `<输入> → [skill] → <输出>` 示意，让读者不运行也能判断是否适用。这是最先填、也最先被读到的一节。

---

## Phase 1：获取与建图  → §1
目的：建立完整上下文，不急于下结论。
要做的：clone 或读取 → 定位入口（优先 SKILL.md）→ 列出目录结构 / scripts / templates / references / frontmatter / 依赖资源 → 通读关键文件。
要回答：这个 skill 叫什么、谁做的、来源、一句话用途。
另外：把 frontmatter 的 `description` 原文摘进 §1，作为理解这个 skill 的起点；再在 §1 给出 skill 文件夹的**完整文件树**，每个文件 / 目录都注释用途（不只列名字）。

## Phase 2：定位  → §2、§3  ← 检查点在这里
目的：先讲清「它为什么存在」，再深挖。
要回答：
- 它解决什么问题？（用户痛点 / 使用场景 / 原有流程的问题 / 带来的改进）→ §2
- 它适合 / 不适合什么场景？→ §2
- 背后核心理念（2–4 条，如「先规划再执行」「拆解复杂任务」「模板保证稳定输出」）→ §3

**检查点**：把 Phase 1–2 的结论简短呈现给用户，确认方向并问「要重点深挖哪些方面？」，确认后才进入 Phase 3。这是整个流程里唯一的强制检查点——它的作用是在投入深度分析前，及时发现「这个 skill 其实不是你以为的那个」「方向跑偏了」。

## Phase 3：架构拆解  → §4
目的：画出整体结构，讲清模块分工。
要做的：生成架构图（ASCII / mermaid 文本图，如 `User Request → Skill Entry → Planner → Execution Loop → Analyzer → Output → Artifact`）；做模块职责表（模块 / 作用 / 设计思想）。重点是「为什么这样切分模块」，不是罗列有哪些模块。分析模块时引用关键代码 / 结构原文佐证。

## Phase 4：Workflow 分析  → §5
目的：搞清执行流程及每步存在的理由。
要做的：画出执行流程图；对每一步回答三个问题：为什么有这步、解决什么问题、删掉会怎样。这一步最能体现作者的设计权衡。

## Phase 5：Prompt 工程分析  → §6
目的：拆解关键 Prompt 的设计手法。
要做的：按 Role / Task / Constraints / Output Format 分别分析——Role 如何建立角色认知、Task 如何定义目标、Constraints 如何防偷懒提稳定性、Output Format 如何保证一致性；末尾总结最值得学的 Prompt 技巧。如果该 skill 没有明显 Prompt（纯脚本型），就分析它的「指令写法」对应的部分。
**必须先摘原文**：把被分析的关键指令 / Prompt 原文摘出来，再拆解——读者要能对照原句。

## 文件 / 代码结构分析  → §7
目的：理解工程组织。
要做的：分析目录结构、入口设计、脚本与文档的分工、为什么这样组织文件（例如把稳定可复现的逻辑放进脚本、把需要判断的部分留给模型）。引用关键代码片段或目录树原文佐证。

## Phase 6：设计经验提炼  → §8、§9
目的：提炼可迁移的经验（不是总结功能）。
要做的：
- §8：编号列出最值得学习的 10 个设计点，每条一句话讲清为什么值得学。
- §9：可迁移思想 / 可复用组件（Workflow 模板、Prompt 模板、输出模板、Agent Pattern）/ 作者隐含经验（为什么加规划阶段、为什么用 Reflection、为什么多步）；标明可迁移到哪类 agent。

## Phase 7：反向重设计  → §10
目的：用自己的话重构一遍，检验是否真懂了。
输出框架：`Original Skill → Design Principles → My Improved Version`，并回答：可以保留什么 / 可以优化什么 / 可以新增什么能力。不是要否定原作者，而是把它的设计原则据为己有。

## SOP 提炼  → §11
目的：把 skill 的具体流程**泛化成可迁移的 SOP**，让读者即使不用这个 skill，也懂「这类问题一般该怎么解决」。
要做的：从 skill 的实际步骤里抽象出标准流程——编号步骤、泛化到同类任务（别只复述这个 skill 的具体动作）；点出流程背后最核心的一两条原则。可提炼一条或多条 SOP。
